1. COMPLEXITY AND BIG O

Lesson 1.1: Why Efficiency Matters

There is often more than one way to solve a problem. Two approaches may produce exactly the same result, but one may require far more work than the other. This difference may not matter when we are working with ten items, but it can become enormous when we are working with thousands or millions of items.

Suppose we have a list containing 100,000 names and want to find both Alice and Bob. We could search through the entire list for Alice and then begin again and search for Bob. In the worst case, we would examine 200,000 names. A better approach would be to search for both names at the same time. We would examine each name once and perform at most 100,000 checks.

Both approaches give us the same answer, but the second requires half as much work. Complexity gives us a way to describe differences like this and understand how well an approach will continue to work as the amount of data grows.

Lesson 1.2: Big O and Input Size

Computer scientists commonly describe complexity using Big O notation. Big O does not tell us exactly how many seconds a program will take to run. Instead, it describes how the amount of work grows as the amount of data grows.

We use the letter n to represent the amount of data. If an array contains 100 items, then n is 100. If it contains one million items, then n is one million.

Constant Complexity: O(1)

Some tasks require the same amount of work regardless of how much data we have. For example, if we want the first item in an array, we can go directly to index 0. It does not matter whether the array contains ten items or ten million items. The task still requires the same amount of work.

We describe this as O(1), or constant complexity.

Linear Complexity: O(n)

Other tasks require more work as the amount of data grows. Suppose we search through an array one item at a time. If the array contains twice as many items, the search may require twice as much work. If it contains ten times as many items, it may require ten times as much work.

The amount of work grows with the number of items. If we double the amount of data, we roughly double the amount of work. We describe this as O(n), or linear complexity.

Big O focuses on this pattern of growth. It helps us understand whether an approach will continue to work well when the amount of data becomes much larger.

Lesson 1.3: Recognizing Complexity in Loops

Loops often make complexity easy to see because we can ask how many times the code inside the loop will run.

Linear Growth

A loop that examines every item in an array runs once for each item. If the array contains n items, the loop runs n times. Its complexity is O(n). 

for (const animal of animals) {
    // Examine each animal.
}

Constant Multipliers

Suppose we loop through the same array twice. The first loop runs n times, and the second loop also runs n times. Together, they perform about 2n operations. 

for (const animal of animals) {
    // First task.
}

for (const animal of animals) {
    // Second task.
}

Big O ignores constant multipliers such as 2. Whether we examine each item once, twice, or five times, the amount of work still grows with the number of items. Two separate loops are therefore O(n), not O(2n).

Quadratic Growth

A nested loop behaves differently. For every item examined by the outer loop, the inner loop examines every item again. 

for (const firstAnimal of animals) {
    for (const secondAnimal of animals) {
        // Compare the two animals.
    }
}

If the array contains n items, the outer loop runs n times. During each of those runs, the inner loop also runs n times. 

n × n = n²

The complexity is O(n²), pronounced “Big O of n squared.”

If the array contains 100 items, the inner section may run 10,000 times. If the array contains 1,000 items, it may run 1,000,000 times. The amount of work grows much more quickly than it does with a single loop.

Cubic Growth

If we place a third loop inside the first two, the work grows again. 

for (const firstItem of items) {
    for (const secondItem of items) {
        for (const thirdItem of items) {
            // Examine this combination.
        }
    }
}

Each loop depends on n, so the total amount of work is: 

n × n × n = n³

The complexity is O(n³).

Constant Work Inside a Loop

Not every loop inside another loop creates O(n²) complexity. Consider an inner loop that always runs exactly five times. 

for (const animal of animals) {
    for (let count = 0; count < 5; count++) {
        // Repeat five times.
    }
}

The outer loop runs n times, but the inner loop does not grow with the amount of data. It always runs five times. This gives us approximately 5n operations.

Big O ignores the constant multiplier, so the complexity is still O(n).

Examining Part of the Data

A loop may examine only part of an array. For example, the following loop examines every other item: 

for (let index = 0; index < animals.length; index += 2) {
    // Examine every other animal.
}

This loop performs approximately n ÷ 2 operations. It does less work than examining every item, but the amount of work still grows with the size of the array. If the array doubles in size, the work also roughly doubles.

Its complexity is therefore still O(n).

Lesson 1.4: Combining Different Kinds of Work

A program may contain several sections with different levels of complexity. To determine the complexity of the entire program, we first consider each section separately.

Suppose a program contains one regular loop followed by a pair of nested loops: 

for (const item of items) {
    // Examine each item.
}

for (const firstItem of items) {
    for (const secondItem of items) {
        // Compare the two items.
    }
}

The first loop is O(n), while the nested loops are O(n²). If we include both parts, the amount of work can be written as: 

O(n² + n)

However, n² grows much faster than n. When n becomes large, the work performed by the regular loop becomes relatively unimportant compared with the work performed by the nested loops. We therefore keep only the fastest-growing term: 

O(n²)

Big O is meant to show the general pattern of growth, not to count every operation. For this reason, we ignore constant multipliers and smaller terms.

A loop that runs through half of an array performs approximately n ÷ 2 operations: 

for (let index = 0; index < items.length / 2; index++) {
    // Examine half of the items.
}

This loop performs less work than one that examines the entire array, but the amount of work still grows with n. If the array doubles in size, the loop performs roughly twice as much work. Its complexity is still O(n).

The same reasoning applies when a loop examines every other item: 

for (let index = 0; index < items.length; index += 2) {
    // Examine every other item.
}

Changing the exact number of operations does not necessarily change the pattern of growth.

Exam questions may also include a loop in which the value doubles during every repetition: 

for (let number = 1; number <= items.length; number = number * 2) {
    // 1, 2, 4, 8, 16...
}

This is not a particularly common way to write everyday code, but it tests whether we understand logarithmic growth. The loop reaches the end quickly because the value doubles each time.

Lesson 1.5: Logarithmic Growth

Suppose we have one long strip of paper and want to divide it evenly among eight people. We first divide the strip into two pieces. We then divide both of those pieces, giving us four pieces. After one more round of division, we have eight pieces. 

Round 0: 1 piece
Round 1: 2 pieces
Round 2: 4 pieces
Round 3: 8 pieces

We can draw this process graphically:

                     1
                   /   \
                  2     3
                 / \   / \
                4   5 6   7

The number of pieces doubles during every round. The question is: how many rounds did we need? In other words, how tall is our tree?

We can solve this mathematically:

2ˣ = 8

We can see that:

2³ = 8

Therefore, x is 3.

In math class, we learned that we can solve for x using a logarithm: 

log₂(8) = 3

Read this as “the base-two logarithm of eight is three.”

We can also find the answer by starting with eight and repeatedly dividing by two: 

8 ÷ 2 = 4
4 ÷ 2 = 2
2 ÷ 2 = 1

Once again, it takes three steps.

When an algorithm cuts the remaining work in half during each step, its complexity is O(log n). Even when the amount of data becomes very large, we need relatively few additional steps.

It is important not to confuse O(log n) with O(n log n). If we follow one path while repeatedly cutting the possibilities in half, the complexity is O(log n). If we process all n items across log n levels, as merge sort does, the complexity is O(n log n).

Lesson 1.6: Comparing Linear Search and Binary Search

Linear Search

A linear search checks each value one by one until it finds the desired value or reaches the end of the list.

If the desired value appears near the beginning, the search finishes quickly. If the value appears near the end or does not exist, the program must examine every item.

Since the number of checks grows with the number of items, linear search has a complexity of O(n).

Binary Search

Binary search takes advantage of sorted data. Rather than checking every value, it looks near the middle and uses that value to eliminate half of the remaining possibilities.

Suppose we want to find 70 in this sorted list: 

10, 20, 30, 40, 50, 60, 70, 80

We begin near the middle and examine 40. Since 70 is greater than 40, we know that 70 cannot appear in the left half of the list. We can immediately eliminate: 

10, 20, 30, 40

We continue with the remaining values:

50, 60, 70, 80

We again look near the middle and eliminate another half of the possibilities. We continue until we find 70 or determine that it is not present.

Because binary search cuts the remaining search area roughly in half during every step, its complexity is O(log n).

The difference becomes dramatic when the list is large. A linear search through one million values may require one million comparisons. A binary search through one million sorted values requires only about twenty comparisons.

Binary search is much faster, but it comes with an important requirement: the information must already be sorted. If the values are not sorted, looking at the middle does not tell us which half can be eliminated.

Best, Average, and Worst Cases

The amount of work performed by an algorithm may depend on the data it receives.

For a linear search, the best case occurs when the desired item appears first. The program finds it immediately and stops.

The average case occurs when the desired item appears somewhere near the middle of the list.

The worst case occurs when the item appears last or does not exist. The program must search through the entire list.

Lesson 1.7: Binary Trees

A binary tree is a structure in which each item can connect to no more than two items below it. 

                40
              /    \
            20      60
           /  \    /  \
         10   30  50   70

This tree is organized so that smaller values appear to the left and larger values appear to the right. A tree organized in this way is called a binary search tree.

Suppose we want to find 70. We begin at 40. Since 70 is larger than 40, we move to the right and reach 60. Since 70 is also larger than 60, we move right again and find 70.

We do not need to examine 10, 20, 30, or 50. At each step, the organization of the tree tells us which direction to follow and allows us to ignore the other part of the tree.

When a binary tree is balanced, its values are spread across both sides rather than forming one long branch. The number of values approximately doubles at each new level: 

Level 0: 1 item
Level 1: 2 items
Level 2: 4 items
Level 3: 8 items

As a result, a balanced binary tree can contain many values without becoming very tall. Searching the tree commonly requires us to move down only one branch, giving us O(log n) complexity.

However, this depends on the shape of the tree. Imagine that the values were added in increasing order and formed a long chain: 

10
  \
   20
     \
      30
        \
         40

This is still a binary tree, but it no longer gives us the same advantage. To find 40, we must move through every value. Searching a badly unbalanced tree can therefore take O(n) time.

The structure of the data matters. A tree does not automatically provide a fast search. It must remain reasonably balanced for us to eliminate a large portion of the remaining values during each step.

Lesson 1.8: Sorting Algorithms

A sorting algorithm rearranges values into a particular order. We might arrange numbers from smallest to largest, names in alphabetical order, or products from least expensive to most expensive.

There are many ways to sort information. Some approaches are easy to understand but become slow when the list grows. Other approaches are more complicated but handle large amounts of data much more efficiently.

Selection Sort

Selection sort repeatedly finds the smallest remaining value and moves it into the next open position.

Suppose we begin with:

7, 3, 5, 2

We examine the entire list and find that 2 is the smallest value. We move it into the first position. We then ignore the first position and find the smallest value in the remaining portion of the list. We continue until every value has been placed in the correct position.

Selection sort must repeatedly search through the unsorted section. The first search examines nearly n values, the next examines nearly n values again, and the process continues until the list is sorted.

Its complexity is O(n²). Even if the list is already sorted, selection sort still searches through the remaining values to confirm which one is smallest.

Insertion Sort

Insertion sort builds a sorted portion of the list one value at a time. Each new value is moved into the correct position among the values that have already been sorted.

Insertion sort is similar to arranging playing cards in your hand. Each time you receive a new card, you slide it into the correct position among the cards you already hold.

In the worst case, each new value must move past nearly every value that came before it. This gives insertion sort a worst-case complexity of O(n²).

However, insertion sort can be efficient when the values are already sorted or nearly sorted. If every value is already in the correct position, the algorithm can move through the list without repeatedly shifting items. Its best-case complexity is O(n).

Merge Sort

Merge sort repeatedly divides the data in half until each section contains one item. It then combines the items into sorted groups of two, combines those into sorted groups of four, and continues until the entire list has been rebuilt in order.

This creates the same familiar tree structure we saw earlier. The number of values is n, while the height of the tree is log n.

At each level, merge sort must process all n values. Since there are log n levels, the total complexity is: 

O(n log n)

Merge sort always provides O(n log n) performance. However, it creates temporary arrays while dividing and combining the data, so it uses additional memory.

Merge sort is also a stable sort. This means that when two items have the same sorting value, they remain in their original order.

Suppose we sort students by grade:

Alex: 90
Jordan: 80
Sam: 90

A stable sort keeps Alex before Sam because Alex appeared first in the original list, even though both students have the same grade.

Quicksort

Quicksort, sometimes called pivot sort when introducing the idea, also divides the data into smaller sections. It begins by choosing one value called a pivot.

Values smaller than the pivot are moved to one side, while larger values are moved to the other. The same process is then repeated within each section.

The pivot may or may not divide the data evenly. If we choose a value near the middle, we split the data into two useful sections and get approximately O(n log n) performance.

If we are unlucky and repeatedly choose one of the smallest or largest values, one section may contain almost all of the remaining data. Quicksort then divides the problem very poorly and can fall to O(n²).

Quicksort is often extremely fast, but its performance depends on how well the pivots divide the data.

Traditional quicksort is not stable. If two items have the same sorting value, quicksort may reverse their original order. This is an important difference between traditional quicksort and merge sort.

Sorting in Real Programs

These algorithms are not merely classroom exercises. Programming languages and system libraries use the same ideas when sorting real data.

For example, Apple guarantees that Swift's built-in sort() and sorted() operations are stable and have O(n log n) complexity. Apple does not promise that these operations use merge sort, quicksort, or any other particular algorithm. This allows the implementation to change while preserving the behavior programmers depend on.

JavaScript follows a similar approach. Its built-in sort() must be stable, but different JavaScript engines may use different algorithms internally.

Lesson 1.9: Comparing Sorting Algorithms

Algorithm Best Case Average Case Worst Case
Selection Sort O(n²) O(n²) O(n²)
Insertion Sort O(n) O(n²) O(n²)
Merge Sort O(n log n) O(n log n) O(n log n)
Quicksort O(n log n) O(n log n) O(n²)

Selection sort is simple, but it performs O(n²) work even when the values are already sorted.

Insertion sort also has an average and worst-case complexity of O(n²), but it can perform well when the list is small or already close to sorted.

Merge sort always provides O(n log n) performance and is stable. However, it creates temporary arrays while combining the data, so it uses additional memory.

Quicksort usually provides O(n log n) performance and is often extremely fast. However, a series of poor pivots can produce an O(n²) worst case. Traditional quicksort is also not stable.

Complexity is not the only consideration when choosing an algorithm. We may also care about memory use, the size and condition of the data, whether equal items must remain in their original order, and how difficult the algorithm is to implement correctly.

Big O does not identify one sorting algorithm as the best in every situation. It gives us a way to understand the tradeoffs and predict what may happen as the list becomes large.

Lesson 1.10: Common Complexity Classes

We have now seen several common patterns of growth:

O(1)
O(log n)
O(n)
O(n log n)
O(n²)
O(n³)
O(2ⁿ)

These are listed from slower growth to faster growth.

An O(1) operation requires roughly the same amount of work regardless of the amount of data.

An O(log n) algorithm repeatedly cuts the remaining possibilities into smaller sections.

An O(n) algorithm performs work that grows with the number of items.

An O(n log n) algorithm commonly processes all n items across log n levels.

An O(n²) algorithm commonly compares every item with every other item.

An O(n³) algorithm may examine every possible combination of three items.

Exponential Complexity: O(2ⁿ)

Exponential complexity appears when every additional input doubles the number of possibilities.

Suppose a program examines every possible result of a series of yes-or-no decisions: 

1 decision:  2 possibilities
2 decisions: 4 possibilities
3 decisions: 8 possibilities
4 decisions: 16 possibilities

With ten decisions, there are 1,024 possible results. With twenty decisions, there are more than one million. With thirty decisions, there are more than one billion.

The input has increased from ten decisions to thirty, but the number of possibilities has grown from about one thousand to more than one billion.

This is why exponential algorithms are dangerous. They may work perfectly well with a small input and then become unusable after the input grows only slightly.

Factorial Complexity: O(n!)

Factorial complexity appears when an algorithm examines every possible ordering of n items. It grows even faster than O(2ⁿ).

Factorials are useful in mathematics when calculating how many different ways a group of items can be arranged. An algorithm that actually examines every one of those arrangements can become impractical after only a small increase in n.

Big O describes how an algorithm grows, but it does not measure its exact running time. A simple O(n²) algorithm may finish faster than a complicated O(n log n) algorithm when the list contains only a few items.

The advantage of the O(n log n) algorithm becomes clear as n grows. Complexity helps us think beyond the small examples on our screen and consider how the same program will behave when it must process thousands or millions of values.
