Chapter 4: Debugging

Introduction

Debugging your code can be challenging and requires perseverance and patience. This is one of the reasons developers place an emphasis on writing good code. It is easier to write good code than to spend time trying to debug bad code. If you do not write clean code, you will pay the price.

When you start a project, it is important to keep things organized and use intuitive names for variables and functions, enabling you to follow the program logic without a lot of effort. Furthermore, by organizing the code into different sections, you do not need to focus on debugging the entire program, but simply a small part of it.

As you add code, run it often. We want to catch errors right away. When you have multiple bugs, it becomes increasingly difficult to figure out what is going on or where the problem is. Always make sure that you are actually running the latest version of your code.

If there is an error, the browser may continue displaying an older version of your app instead. Check that you are seeing the changes you expect, or check the terminal to confirm that the app was updated. Alternatively, it may be convenient to display the app’s start time in the corner of your screen.

Lesson 4.1: Finding the Problem

When something goes wrong, begin by identifying what kind of problem you are seeing.

  1. The code will not build. TypeScript or Vite found a problem before the app could run.
  2. The app stops or silently fails. Something went wrong while the program was running. Sometimes the browser displays an error. Other times, a button or feature simply stops working.
  3. The app runs, but the result is wrong. The code is valid, but the program does not behave as intended.
  4. The app cannot load data. A file may be missing, a server request may have failed, or the returned data may not match what the app expects.

Use the following tools to help locate the problem:

What Happened Where to Look
TypeScript error VS Code Problems panel
Vite or import problem Terminal or browser error screen
App crashes or does nothing Browser Console
File or server request fails Browser Network tab

When part of a JavaScript app fails, the entire page may remain visible. A button or feature may simply stop working, so check the browser Console whenever nothing appears to happen.

TypeScript checks the types in our code before it runs, but it cannot guarantee that data loaded from a file, storage, or server actually has the expected structure. This is one reason runtime errors can still occur even when TypeScript did not report a problem.

Lesson 4.2: Checking Values

A simple way to debug a program is to display information while it runs. This helps us confirm whether a function ran, what value a variable contains, how far the program reached, and where the result first became incorrect.

We can create a temporary label and add it to the page:

const debugOutput = document.createElement("p");
document.body.appendChild(debugOutput);

We can then display the value we want to check:

debugOutput.textContent = `score: ${score}`;

We can also add several messages to the same element:

debugOutput.textContent =
    debugOutput.textContent + `Loaded user: ${userName}\n`;

debugOutput.textContent =
    debugOutput.textContent + `Current score: ${score}\n`;

Move these statements through the code to see how far the program gets: 

debugOutput.textContent =
    debugOutput.textContent + "Starting calculation\n";

calculateScore();

debugOutput.textContent =
    debugOutput.textContent + "Finished calculation\n";

If the second message never appears, the problem probably occurred inside calculateScore().

As an alternative way to print debugging information, we can send it to the browser Console: 

console.log(score);

In Chrome on a Mac, select View → Developer → Developer Tools, and then select the Console tab. The Console contains a great deal of other information. Ignore anything that is not related to the values you printed or errors connected to your app.

Temporary debugging messages should be removed after the problem has been fixed.

Lesson 4.3: A Basic Debugging Process

  1. Confirm that the newest code is running.
  2. Read the error message.
  3. Find the file and line number.
  4. Identify the smallest section that could contain the problem.
  5. Check the values going into that section.
  6. Fix one problem at a time.
  7. Run the code again.

Lesson 4.4: Walking Through Code

A debugger allows us to pause the program and examine it one line at a time.

Open the app in Chrome, select View → Developer → Developer Tools, and open the Sources tab. Find the TypeScript file containing the code you want to examine.

Our goal is to stop the program at a particular location and then move through it one line at a time. As we move through the code, we can watch variables change and see exactly which statements run.

Click the line number next to a statement to add a breakpoint. A breakpoint tells the browser to pause before running that line.

Run the app and perform the action that reaches the breakpoint. For example, click the button that calls the function you are debugging. When the program pauses, Chrome will show the current line and the values of nearby variables.

Use Step over to run the current line and move to the next one. Continue stepping through the code while watching how the variable values change. If a value first becomes incorrect after a particular line, that line or the function it calls is probably connected to the problem.

Use Resume to continue running the app normally. Click the line number again when you want to remove the breakpoint.

When debugging, focus on the smallest section that could contain the problem. Check the values going into that section, walk through its code, and fix one problem at a time.

Lesson 4.5: Common Runtime Errors

Runtime errors occur after the app has started. The code may build successfully, but something goes wrong while it is running.

TypeScript checks the types in the code we write, but it cannot guarantee that values loaded from HTML, storage, files, or online services actually contain what we expect. It also cannot prevent every logical mistake, such as a loop that never ends.

A common problem is trying to use a value that is null or undefined. This often happens when an HTML element was not found, data was never loaded, or a key did not exist. 

const userName = userData.name;

This fails if userData is undefined.

A similar problem occurs when an object does not contain the property we expected. This is especially common with data loaded from a file, storage, or server.

Functions can also receive unexpected values. A function may expect a number but receive an empty string, undefined, or some other value that causes the calculation to fail or produce the wrong result.

Finally, a loop may never reach its stopping condition, or a function may continue calling itself without reaching an ending point. This can cause the app to freeze or eventually stop with an error.

When a runtime error occurs, look at the error message and line number, then check the values being used on that line.
