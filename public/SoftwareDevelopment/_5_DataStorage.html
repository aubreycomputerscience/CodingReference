Chapter 5: Saving Data

Web applications often need to save information so that it remains available after the page is refreshed or the browser is closed. The appropriate storage tool depends on how much information we need to save, how it is organized, and whether it must be shared with other users or devices.

Need Appropriate Tool
A theme setting, username, or a few simple values localStorage
Structured records, lists, or offline app data IndexedDB
Data shared among users or devices A server database
Complex relational queries Usually a server database using SQL
Local structured data with cleaner syntax IndexedDB through idb or idb-keyval

Saving Simple Values with localStorage

localStorage provides a simple way to save small amounts of data to disk through the browser. It works like a dictionary: we store a value for a key and later use that key to retrieve the value.

Suppose our program contains two number input fields:

function save(): void {
    const x = Number(xInputField.value);
    const y = Number(yInputField.value);

    localStorage.setItem("x", String(x));
    localStorage.setItem("y", String(y));
}

function load(): void {
    const savedX = localStorage.getItem("x");
    const savedY = localStorage.getItem("y");

    if (savedX !== null) xInputField.value = savedX;
    if (savedY !== null) yInputField.value = savedY;
}

localStorage only stores strings. We therefore use String() when saving a number. When we place the saved value back into an input field, it can remain a string because an input field’s value property is also a string. If we wanted to use the saved value in a calculation, we would convert it back into a number: 

const x = Number(localStorage.getItem("x"));

getItem() returns null when nothing has been saved with that key. We check for null before using the returned value so that we do not replace the input field with missing data.

Calling setItem() again with the same key replaces the previous value. We can also remove one saved value or clear everything saved by the application: 

localStorage.removeItem("x");
localStorage.clear();

localStorage works well for a few simple values, but it becomes awkward when we need to save lists or larger structured objects. For that kind of data, we will use IndexedDB through idb-keyval.

Saving Data with idb-keyval

idb-keyval allows us to save data to disk through the browser using simple keys and values. The saved data remains available after the page is refreshed or the browser is closed. 

import * as db from "idb-keyval"; // Call db.get(), db.set(), db.del(), or db.clear().

type UserData = {
    userName: string;
    favoriteColor: string;
};

submitButton.onclick = async () => {
    const userName = userNameInputField.value;
    const favoriteColor = favoriteColorInputField.value;

    if (userName === "" || favoriteColor === "") {
        return; // Do not save until the user has entered both values.
    }

    await saveUserData(userName, favoriteColor); // Stop here until the save is complete.
    refreshUI(); // Continue after the data has been saved.
};

async function saveUserData(userName: string, favoriteColor: string): Promise<void> {
    const userData: UserData = {
        userName,
        favoriteColor
    };

    await db.set("userData", userData);
}

Saving data may take some time. We do not want the entire program or interface to stop while the browser completes the save. Instead, await tells JavaScript to stop this function at that line and resume it after the requested operation has finished. In this example, refreshUI() does not run until saveUserData() is complete.

A function that contains await must be marked async. This lets TypeScript know that the function may pause and resume later. Because the function does not finish immediately, it returns a Promise rather than returning its final result right away. 

async function myFunction(): Promise<void> {
    await someAsyncOperation();
}

Promise<void> means that the function promises to finish later but will not return a value. A function that eventually returns user data might instead use: 

async function getUserData(): Promise<UserData | undefined> {
    return db.get<UserData>("userData");
}

db.get<UserData>() tells TypeScript that we expect the saved value to have the UserData type. The angle brackets are a generic type argument, not destructuring. Because no value may have been saved with that key, the function may still return undefined.

We can load the saved data using the same key:

async function loadUserData(): Promise<void> {
    const userData = await db.get<UserData>("userData");

    if (userData === undefined) return; // Nothing has been saved with this key.

    userNameInputField.value = userData.userName;
    favoriteColorInputField.value = userData.favoriteColor;
}

The string "userData" is the key. The UserData object is the value saved for that key. Calling db.set() again with the same key replaces the previously saved value.

Use db.del() to remove the value stored for one key: 

await db.del("userData");

Use db.clear() to remove every key and value stored by idb-keyval: 

await db.clear();

Be careful with clear(). It removes everything in the store, not just the user data.

Installing idb-keyval

If idb-keyval is not already installed in the project, run: 

npm install idb-keyval

You only need to add it to the project once. npm records the library in package.json and package-lock.json, so the project remembers that it requires idb-keyval.

After someone downloads a copy of the project, they run:

npm install

npm reads the project files and installs idb-keyval, Vite, and any other required libraries.

Saving Data Online

localStorage and IndexedDB save data on the user’s device. This works well when the data belongs to one installation of an application, but it does not allow the same information to be shared automatically between devices or users. A messaging application, for example, needs to store messages online so that every participant can receive them.

One way to add online storage is to use Firebase, a collection of services provided by Google. Firebase is often described as a serverless backend. Serverless does not mean that no servers are involved. It means that Google runs and manages the servers, allowing us to use the service without building and maintaining our own backend server.

Firebase provides different storage tools for different kinds of data.

Cloud Storage

Cloud Storage is used to save files, such as images, videos, audio recordings, documents, or game-level files. The files are stored online and can be uploaded or downloaded by an application.

Firebase Databases

Firebase also provides online databases for structured application data. Cloud Firestore stores data in documents organized into collections. Each document contains key-value pairs, making it useful for information such as users, assignments, posts, or saved games.

Firebase Realtime Database stores data as a large JSON structure. JSON is a common text format for organizing data using objects, keys, values, and lists. When the data changes, Firebase can automatically send the updated information to connected applications. This makes it useful for applications such as messaging, shared game state, or live status displays.

Both databases are NoSQL databases built largely around keys and values rather than traditional SQL tables and joins. SQL is a language used to store, organize, and query data in relational databases made from tables and rows. Firestore provides more flexible organization and queries, while Realtime Database is particularly well suited to simple data structures that must synchronize quickly.

Using these services requires creating a Firebase project through a Google account, connecting the application to that project, and setting rules that determine who may read or change the data. We will not work through those implementation details yet, but these tools provide a relatively accessible way to add shared online storage without creating our own server.
